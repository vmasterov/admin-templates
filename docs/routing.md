# Роутинг — дизайн по RADIO

Основа — ТЗ из [`spec.md`](./spec.md). Первый цикл RADIO, проходится вместе с Claude.

## R — Requirements

### Функциональные

1. **Маршруты:** `/login`, `/` (редирект), `/articles`, `/articles/create`, `/articles/:id/edit`,
   `/comments`, `*`.
2. **Лейаут:** защищённые страницы рендерятся внутри общего лейаута, `/login` и NotFound — без него.
3. **Уровни доступа:**
   - *защищённый*: гость → `/login`;
   - *только для гостей*: вошедший → `/articles`;
   - *для всех*: без проверок.
4. **Состояние сессии:** загружается / гость / вошёл. Пока сессия загружается, guards ничего не решают,
   показывается индикатор загрузки (иначе после перезагрузки страницы вошедшего выкинет на `/login`).
5. **Редиректы:** `/` → `/articles`; после входа → `/`; после выхода → `/login`.
6. **404:** неизвестный URL показывает NotFound на том же адресе (без редиректа). Несуществующий `:id`
   обрабатывает страница — рендерит тот же NotFound; роутер к API не обращается.
7. **Конфиг маршрутов:** у каждого маршрута есть имя, все маршруты описаны в одном месте.
8. **Производное из конфига:** меню сайдбара (активный пункт — по префиксу пути).
   Заголовок вкладки и хлебные крошки — отложены (PLAN-UPDATE-2026-10-25).
9. **Переходы:** только через `buildPath(name, params)`. Параметры типизированы, пропущенный параметр —
   ошибка TS.

### Нефункциональные

10. Core (типы конфига маршрутов, guards, `buildPath`, меню) — чистый TS в `shared/lib`,
    без импорта React или Vue. Во Vue переносится без правок.
11. Адаптеры только переводят конфиг в формат react-router или vue-router и вызывают guards.
12. Guards — список независимых чистых функций. Новая проверка — новый guard, существующие не меняются
    (OCP).
13. Guards получают состояние сессии на вход и не знают, где и как она хранится (DIP).
14. Core покрыт unit-тестами.

### Вне рамок

- Собственный роутер.
- Вложенность глубже лейаута.
- Query-параметры (появятся с Tabs и DataTable).
- Заголовок вкладки и хлебные крошки — отложены (вернуться, если останется время).
- Анимации переходов.
- Проверка существования сущностей в роутере.
- Настоящая авторизация (пока заглушка сессии; хранение — тема «Авторизация»).
- Lazy loading — шаг O.
- Роли и возврат на исходную страницу после входа — новые требования сессии 5.

## A — Architecture

### Структура (React; во Vue та же, с `.vue` вместо `.tsx`)

```
app/
  config/
    pages.config.ts      имя маршрута → компонент страницы (Record<RouteName, Component>)
    guards.config.ts     политика доступа: [requireAuth('login'), guestOnly('articles')]
  layout/layout.tsx      шапка + сайдбар
  adapters/routerAdapter.ts  конфиг + страницы → формат библиотеки; вызов checkAccess
pages/                   Login, Articles, ArticleEdit, Comments, NotFound
features/auth/           сессия (пока заглушка), тип TSession
shared/
  config/router.config.ts  конфиг маршрутов блога + привязка фабрик core
  lib/router/              core — чистый TS, про блог не знает
    types/    TRouterConfig, TAccessContext
    helpers/  createBuildPath, checkAccess, getMenuItems
    guards/   requireAuth, guestOnly (фабрики)
```

### Зависимости

```
app ──→ pages ──→ features/auth
 │         │
 │         └──→ shared/config
 └──→ features/auth, shared/config, shared/lib/router
shared/config ──→ shared/lib/router   (не наоборот)
```

### Решения и причины

- **Роутинг — инфраструктура, а не фича.** Фича — действие пользователя; адаптер импортирует `pages`,
  поэтому может жить только в `app`.
- **Конфиг маршрутов — в `shared/config`.** Он нужен страницам (ссылки), фичам (переходы) и лейауту
  (меню). Из `features` соседние фичи его импортировать не могли бы. `shared/config` — единственное место
  в `shared`, где допустимо знание о проекте.
- **Компоненты отдельно от конфига** (`pages.config.ts` в `app`). Конфиг остаётся одинаковым для
  React и Vue; `Record<RouteName, Component>` даёт ошибку TS, если страница для маршрута забыта.
- **Guards: механизм в `shared`, политика в `app/config`.** Фабрика `requireAuth(redirectTo)` универсальна;
  какие guards и с какими адресами редиректа — решает проект. Роли на сессии 5 = новая фабрика +
  строка в `guards.config.ts`.
- **DIP для сессии.** `TAccessContext` (`status`, `role?`) объявлен в core — абстракцией владеет
  потребитель. Полная сессия — в `features/auth`. Адаптер переводит одно в другое и передаёт параметром
  (DI). `Session` не выносится в `shared`: роутеру нужны два поля, а не вся сессия (ISP).
- **Фабрики в core.** Core не импортирует конфиг блога; конфиг привязывается к нему один раз в
  `shared/config` (`createBuildPath(routes)`). Имена маршрутов — литеральный union из ключей конфига,
  отдельные константы имён не нужны.
- **Адаптер — тонкий клей без логики доступа.** Обязанности: перевести конфиг в формат
  библиотеки (лейаут как родитель, `*` — NotFound), вызвать `checkAccess` при навигации, показать
  загрузку, пока сессия неизвестна. Проверка: `if` про доступ в адаптере
  означает, что логика утекла из core.

## D — Data model

### Типы core (`shared/lib/router/types`)

```ts
type TAccess = 'protected' | 'guest' | 'public';

type TPageRoute = {
  path: string;
  access: TAccess;
  menu?: { label: string };   // есть поле = пункт меню
};

type TRedirectRoute = {
  path: string;
  redirectTo: string;         // имя маршрута; проверка имени — шаг I
};

type TRoute = TPageRoute | TRedirectRoute;
type TRouterConfig = Record<string, TRoute>;

type TAccessContext = { status: 'guest' } | { status: 'authenticated' };
```

В проекте: `const routes = { … } as const satisfies TRouterConfig`. `satisfies` проверяет форму, но
сохраняет конкретные ключи и пути: `keyof typeof routes` — union имён, пути — литералы.

### Решения и причины

- **Имя маршрута — ключ конфига**, в значении его нет (иначе два источника правды). Имя
  описывает шаблон (`articleEdit`), а не конкретную статью.
- **Три уровня доступа, а не `boolean`.** Уровень описывает маршрут; каждый guard смотрит
  только на свой уровень (`requireAuth` — `protected`, `guestOnly` — `guest`, `public` никто).
- **Два вида записей: страница | редирект.** Тип запрещает бессмысленные сочетания (редирект с
  `menu`). `/` → `/articles` — безусловный редирект, не guard: он не зависит от сессии.
- **`*` добавляет адаптер**, а не конфиг: синтаксис catch-all у библиотек разный, а `buildPath`
  к нему никто не строит.
- **Лейаут выводится из `access`**: `protected` — в лейауте. Это неявная связь (поэтому 404 без
  лейаута); явное поле дало бы гибкость ценой лишнего знания конфига. Сейчас приемлемо.
- **`TAccessContext` без `loading`.** Загрузку проверяет адаптер и показывает лоадер; guards
  вызываются только с известным статусом — тип делает «загрузку в guard» непредставимой. Роли
  нет (YAGNI); на сессии 5 — `{ status: 'authenticated'; role }`.
- **Guard возвращает имя маршрута или `null`.** Имя, а не путь: путь `/login` не дублируется в
  `guards.config`, имя проверяется TS, адаптер превращает его в путь через `buildPath`. Объект
  `{ allow } | { redirect }` — если появятся другие исходы (403, `replace`).
- **Меню плоское:** `getMenuItems` → `{ name, label, path }[]` — готовые данные для отрисовки,
  лейаут не знает устройства конфига. Активный пункт — сравнение `path` с текущим URL по
  префиксу. В меню только маршруты без параметров.
- **`title` и `parent` нет** — отложены вместе с заголовком вкладки и крошками. Когда
  вернёмся: `title` — основной текст, `parent` — по имени, `children` вычисляется.

### Статичное и динамичное

- **Статичное исходное:** конфиг маршрутов, `pages.config`, `guards.config`.
- **Динамичное исходное — только два источника:** сессия (владеет `features/auth`) и текущий
  URL (владеет библиотека роутинга). Адаптер сессию не хранит, а читает и переводит.
- **Производное статичное** (считается один раз): пункты меню, структура маршрутов с лейаутом.
- **Производное динамичное** (пересчитывается, в state не хранится): результат guards,
  активный пункт меню.

### Перенесено на следующие шаги

- **I:** см. раздел «I — Interface».
- **O:** обёртка `AppLink` в `shared/ui` — если понадобится prefetch страниц или единое поведение
  ссылок. До тех пор — `Link` / `RouterLink` библиотеки + `buildPath`.

## I — Interface

Контракты пишутся типами в `shared/lib/router/types` (без реализаций). Решено: отдельные
фабрики, а не одна `createRouter`. Имена выводятся из конкретного конфига через дженерик
`C extends TRouterConfig` (`keyof C & string`).

### Чек-лист

- [x] `TRouterConfig`, `TRoute` (страница | редирект, взаимоисключающие через `?: never`), `TAccess`
- [x] `TKey<C>`, `TPageKey<C>` — имена маршрутов и страниц; `pages.config`:
      `Record<TPageKey<typeof routes>, ComponentType>`
- [x] `TAccessContext`
- [x] `TGuard<C>` — `(ctx, route: TPageRoute) => TPageKey<C> | null`; `TCreateGuard<C>` — фабрика
      guard'а по цели редиректа
- [x] `TCheckAccess<C>` — результат `TPageKey<C> | null` (решает первый сработавший guard; порядок в
      `guards.config` = приоритет), guards — `readonly TGuard<C>[]`
- [x] Проверка `redirectTo` — **заменена unit-тестом валидности конфига** (шаг кода): каждый
      `redirectTo` ведёт на существующую страницу, пути уникальны и начинаются с `/`. Тип-валидатор
      через `defineRoutes` — паттерн библиотек (Vite, TanStack Router), для одного редиректа переусложнение.
- [x] `TPathParams<P>` — рекурсивный разбор пути (template literal + `infer`):
      `'/articles/:id/edit'` → `'id'`
- [x] `TPathArg<Param>`, `TBuildPath<C>`, `TCreateBuildPath` — `params` обязателен, только если в пути
      есть `:параметры`
- [x] `TMenuItem<C>` (`name: TPageKey<C>`, `label`, `path`) и `TGetMenuItems` — плоский список
- [x] `TSession` (`features/auth`): `guest | authenticated`, `user` только у вошедшего;
      `TGetSession = () => Promise<TSession>`. Состояния `loading` нет: загрузка живёт внутри
      промиса, middleware его ждёт. `toAccessContext` не нужна: сессия структурно подходит
      под `TAccessContext`, соответствие проверяет TS на стыке в адаптере. Типы сессии — в
      `auth`, а не в `shared` (DIP: core объявляет свои литералы сам).
- [x] Точка входа адаптера (`app/adapters/router`): `createRoutes<Config>({ routerConfig, pages,
      layout, notFoundPage, guards, getSession }) => RouteObject[]` — всё статичное приходит
      параметрами (DI, тест подставляет своё). `createBrowserRouter` — отдельно, в сборке
      `app/router.ts` (в тестах — `createMemoryRouter`), один раз на уровне модуля.
- [x] Фабрики middleware (`app`): `TCreateAuthMiddleware(getSession)`,
      `TCreateGuardMiddleware(route: TPageRoute, guards, buildPath)`. `TPages<Config>` — в `app`
      (зависит от React, потребители только в `app`). Ключ `sessionContext = createContext<TSession>()`
      — значение, появится на шаге кода.

**Шаг I закрыт 16.11.2026.** Заглушки `RouteObject` и типа middleware заменить библиотечными
после установки `react-router`.

### Решения по типам

- **Где стоит дженерик.** `Config` фиксируется при вызове фабрики, `RouteName` — при каждом
  вызове `buildPath`.
- **Обязательность параметров — через rest-аргумент с кортежем:** нет параметров → `[]`, есть →
  `[params: Record<…>]`. Проверка на пустоту — `[X] extends [never]` (кортеж отключает
  распределение условного типа).
- **Без лишнего дженерика для `params`:** при выводе типа из аргумента не срабатывает
  проверка лишних свойств (`{ id, idd }` прошло бы).
- **`readonly` — у типа массива, а не у параметра:** `readonly guards` — синтаксис parameter property
  конструктора, запрещён `erasableSyntaxOnly`.
- Вывод параметров работает только на конфиге с путями-литералами (`as const satisfies`).

### Как срабатывают guards (особенности адаптеров)

- Результат `checkAccess` нигде не хранится: вычисляется при переходе и сразу применяется.
- Маршрут по URL находит библиотека; имя прикрепляется при регистрации (Vue — `name`,
  React — `id`/`handle` или маршрут в замыкании обёртки), описание берётся по ключу.
- **Vue:** `router.beforeEach` — возвращённое значение (`true` или `{ name }`) и есть редирект.
  Срабатывает только при переходе → после выхода нужен явный переход на `/login` (в действии
  выхода или `watch` на сессию).
- **React:** middleware react-router (data mode) — см. «Решение: guards в middleware». Как и
  во Vue, срабатывает при переходе → после выхода нужен явный переход на `/login`.
- Риск: ошибка в конфиге (например, `login` защищённый) даёт бесконечный цикл редиректов —
  кандидат для шага O.

### Решение: guards в middleware (13.11.2026)

Было: компонент-обёртка `RouteGuard` (проверка при рендере). Стало: middleware react-router.

**Почему:** так рекомендует документация data mode; проверка идёт до рендера и до loaders
(порядок: корень → родитель → ребёнок → loaders); адаптеры React и Vue устроены одинаково
(middleware ≈ `beforeEach`); guards и `checkAccess` не меняются — меняется только место вызова.

**Как устроено:**
- `features/auth` отдаёт `getSession()` без React и роутера, **с кэшем** (один запрос `/me`, вход и выход
  обновляют кэш): middleware срабатывает на каждом переходе.
- Адаптер: контекст сессии (`createContext`) и middleware авторизации на **корневом**
  маршруте — выше лейаута и `/login`, иначе `guestOnly` останется без сессии.
- Guard-middleware на каждой странице: `createRoutes` создаёт его фабрикой (маршрут в
  замыкании) → `checkAccess` → `throw redirect(buildPath(target))`. Один корневой middleware не
  знает, какая запись конфига совпала; групповые (лейаут + `/login`) хватило бы сейчас,
  но не для ролей сессии 5.
- `RouteGuard` и компонент-лоадер не нужны: при первой загрузке — `HydrateFallback`.
- Выход: очистить кэш сессии + явный переход на `/login`.

**Оценка сложности:** для такого размера хватило бы двух проверок в middleware (~15 строк).
Список guards + `checkAccess` — осознанный учебный запас под шаблон и сессию 5. Если роли не
добавятся без правок — абстракция не окупилась.

## O — Optimizations

| Вопрос | Решение | Приоритет |
|---|---|---|
| Lazy loading страниц | При пяти страницах выигрыша нет. Если понадобится — `lazy` у маршрута, чанки делает Vite | не делаем |
| Цикл редиректов | Ловим в тесте, а не в рантайме: исход guards зависит только от конфига и статуса (два значения) → перебрать все страницы × статусы, повтор адреса в цепочке = падение. Часть теста валидности конфига | сейчас |
| Сбой `/me` (сеть, 500) | Экран ошибки, а не «гость»; 401 = гость. Механизм — `errorElement` / `ErrorBoundary`: middleware бросает не-редирект → ближайший `errorElement` | минимум сейчас (один компонент на корне, иначе отладочный экран роутера); развитие — после R1 |
| Первая загрузка | `HydrateFallback` на корневом маршруте | сейчас (штатный/простой) |
| Медленный переход | В data mode переход ждёт middleware и loaders, всё это время виден *старый* экран. Глобальный индикатор через `useNavigation()` | в срезе (когда появятся loaders) |
| Редирект guard'а | Заменяет запись в истории — «Назад» не возвращает на закрытую страницу. Проверить интеграционным тестом | сейчас |
| a11y: активный пункт меню | `aria-current="page"` — бесплатно через `NavLink` | сейчас |
| a11y: фокус после перехода | На первое поле формы, иначе на заголовок страницы | не делаем |
| Безопасность | Клиентские guards — только UX (сценарий, что видит пользователь). Защита данных — сервер (401 на каждый API без сессии); хранение токена — тема «Авторизация» | на клиенте — ничего; сервер — в срезе |
| `AppLink` | Обёртка ссылки — если понадобится prefetch или единое поведение ссылок | не делаем |

### Тесты

- **Unit (Vitest), сейчас:** `createBuildPath`, guards, `checkAccess`, `getMenuItems`, валидность конфига
  (`redirectTo` → существующая страница, пути уникальны и начинаются с `/`, нет циклов редиректов).
- **Интеграция, сейчас (3–4 сценария):** `createMemoryRouter` + Testing Library, без браузера и сервера
  (фейковый `getSession` — здесь окупается DI): гость → `/articles` → `/login`; вошедший → `/login` →
  `/articles`; неизвестный URL → NotFound; выход → `/login`.
- Middleware отдельно не тестируются — они тонкие, их покрывают сценарии. E2E (Playwright, настоящий
  браузер) — не делаем.
