# Роутинг — дизайн по RADIO

Основа — ТЗ из [`spec.md`](./spec.md). Первый цикл RADIO, проходится вместе с Claude.

## R — Requirements

### Функциональные

1. **Маршруты:** `/login`, `/` (редирект), `/articles`, `/articles/create`, `/articles/:id/edit`,
   `/comments`, `*`.
2. **Лейаут:** защищённые страницы рендерятся внутри общего лейаута, `/login` и NotFound — без него.
3. **Уровни доступа:**
   - *защищённый*: гость → `/login`;
   - *только для гостей*: вошедший → `/articles`;
   - *для всех*: без проверок.
4. **Состояние сессии:** загружается / гость / вошёл. Пока сессия загружается, guards ничего не решают,
   показывается индикатор загрузки (иначе после перезагрузки страницы вошедшего выкинет на `/login`).
5. **Редиректы:** `/` → `/articles`; после входа → `/`; после выхода → `/login`.
6. **404:** неизвестный URL показывает NotFound на том же адресе (без редиректа). Несуществующий `:id`
   обрабатывает страница — рендерит тот же NotFound; роутер к API не обращается.
7. **Конфиг маршрутов:** у каждого маршрута есть имя, все маршруты описаны в одном месте.
8. **Производное из конфига:** меню сайдбара (активный пункт — по префиксу пути).
   Заголовок вкладки и хлебные крошки — отложены (PLAN-UPDATE-2026-10-25).
9. **Переходы:** только через `buildPath(name, params)`. Параметры типизированы, пропущенный параметр —
   ошибка TS.

### Нефункциональные

10. Core (типы конфига маршрутов, guards, `buildPath`, меню) — чистый TS в `shared/lib`,
    без импорта React или Vue. Во Vue переносится без правок.
11. Адаптеры только переводят конфиг в формат react-router или vue-router и вызывают guards.
12. Guards — список независимых чистых функций. Новая проверка — новый guard, существующие не меняются
    (OCP).
13. Guards получают состояние сессии на вход и не знают, где и как она хранится (DIP).
14. Core покрыт unit-тестами.

### Вне рамок

- Собственный роутер.
- Вложенность глубже лейаута.
- Query-параметры (появятся с Tabs и DataTable).
- Заголовок вкладки и хлебные крошки — отложены (вернуться, если останется время).
- Анимации переходов.
- Проверка существования сущностей в роутере.
- Настоящая авторизация (пока заглушка сессии; хранение — тема «Авторизация»).
- Lazy loading — шаг O.
- Роли и возврат на исходную страницу после входа — новые требования сессии 5.

## A — Architecture

### Структура (React; во Vue та же, с `.vue` вместо `.tsx`)

```
app/
  config/
    pages.config.ts      имя маршрута → компонент страницы (Record<RouteName, Component>)
    guards.config.ts     политика доступа: [requireAuth('login'), guestOnly('articles')]
  layout/layout.tsx      шапка + сайдбар
  adapters/routerAdapter.ts  конфиг + страницы → формат библиотеки; вызов checkAccess
pages/                   Login, Articles, ArticleEdit, Comments, NotFound
features/auth/           сессия (пока заглушка), тип TSession
shared/
  config/router.config.ts  конфиг маршрутов блога + привязка фабрик core
  lib/router/              core — чистый TS, про блог не знает
    types/    TRouterConfig, TAccessContext
    helpers/  createBuildPath, checkAccess, getMenuItems
    guards/   requireAuth, guestOnly (фабрики)
```

### Зависимости

```
app ──→ pages ──→ features/auth
 │         │
 │         └──→ shared/config
 └──→ features/auth, shared/config, shared/lib/router
shared/config ──→ shared/lib/router   (не наоборот)
```

### Решения и причины

- **Роутинг — инфраструктура, а не фича.** Фича — действие пользователя; адаптер импортирует `pages`,
  поэтому может жить только в `app`.
- **Конфиг маршрутов — в `shared/config`.** Он нужен страницам (ссылки), фичам (переходы) и лейауту
  (меню). Из `features` соседние фичи его импортировать не могли бы. `shared/config` — единственное место
  в `shared`, где допустимо знание о проекте.
- **Компоненты отдельно от конфига** (`pages.config.ts` в `app`). Конфиг остаётся одинаковым для
  React и Vue; `Record<RouteName, Component>` даёт ошибку TS, если страница для маршрута забыта.
- **Guards: механизм в `shared`, политика в `app/config`.** Фабрика `requireAuth(redirectTo)` универсальна;
  какие guards и с какими адресами редиректа — решает проект. Роли на сессии 5 = новая фабрика +
  строка в `guards.config.ts`.
- **DIP для сессии.** `TAccessContext` (`status`, `role?`) объявлен в core — абстракцией владеет
  потребитель. Полная сессия — в `features/auth`. Адаптер переводит одно в другое и передаёт параметром
  (DI). `Session` не выносится в `shared`: роутеру нужны два поля, а не вся сессия (ISP).
- **Фабрики в core.** Core не импортирует конфиг блога; конфиг привязывается к нему один раз в
  `shared/config` (`createBuildPath(routes)`). Имена маршрутов — литеральный union из ключей конфига,
  отдельные константы имён не нужны.
- **Адаптер — тонкий клей без логики доступа.** Обязанности: перевести конфиг в формат
  библиотеки (лейаут как родитель, `*` — NotFound), вызвать `checkAccess` при навигации, показать
  загрузку, пока сессия неизвестна. Проверка: `if` про доступ в адаптере
  означает, что логика утекла из core.

## D — Data model

### Типы core (`shared/lib/router/types`)

```ts
type TAccess = 'protected' | 'guest' | 'public';

type TPageRoute = {
  path: string;
  access: TAccess;
  menu?: { label: string };   // есть поле = пункт меню
};

type TRedirectRoute = {
  path: string;
  redirectTo: string;         // имя маршрута; проверка имени — шаг I
};

type TRoute = TPageRoute | TRedirectRoute;
type TRouterConfig = Record<string, TRoute>;

type TAccessContext = { status: 'guest' } | { status: 'authenticated' };
```

В проекте: `const routes = { … } as const satisfies TRouterConfig`. `satisfies` проверяет форму, но
сохраняет конкретные ключи и пути: `keyof typeof routes` — union имён, пути — литералы.

### Решения и причины

- **Имя маршрута — ключ конфига**, в значении его нет (иначе два источника правды). Имя
  описывает шаблон (`articleEdit`), а не конкретную статью.
- **Три уровня доступа, а не `boolean`.** Уровень описывает маршрут; каждый guard смотрит
  только на свой уровень (`requireAuth` — `protected`, `guestOnly` — `guest`, `public` никто).
- **Два вида записей: страница | редирект.** Тип запрещает бессмысленные сочетания (редирект с
  `menu`). `/` → `/articles` — безусловный редирект, не guard: он не зависит от сессии.
- **`*` добавляет адаптер**, а не конфиг: синтаксис catch-all у библиотек разный, а `buildPath`
  к нему никто не строит.
- **Лейаут выводится из `access`**: `protected` — в лейауте. Это неявная связь (поэтому 404 без
  лейаута); явное поле дало бы гибкость ценой лишнего знания конфига. Сейчас приемлемо.
- **`TAccessContext` без `loading`.** Загрузку проверяет адаптер и показывает лоадер; guards
  вызываются только с известным статусом — тип делает «загрузку в guard» непредставимой. Роли
  нет (YAGNI); на сессии 5 — `{ status: 'authenticated'; role }`.
- **Guard возвращает имя маршрута или `null`.** Имя, а не путь: путь `/login` не дублируется в
  `guards.config`, имя проверяется TS, адаптер превращает его в путь через `buildPath`. Объект
  `{ allow } | { redirect }` — если появятся другие исходы (403, `replace`).
- **Меню плоское:** `getMenuItems` → `{ name, label, path }[]` — готовые данные для отрисовки,
  лейаут не знает устройства конфига. Активный пункт — сравнение `path` с текущим URL по
  префиксу. В меню только маршруты без параметров.
- **`title` и `parent` нет** — отложены вместе с заголовком вкладки и крошками. Когда
  вернёмся: `title` — основной текст, `parent` — по имени, `children` вычисляется.

### Статичное и динамичное

- **Статичное исходное:** конфиг маршрутов, `pages.config`, `guards.config`.
- **Динамичное исходное — только два источника:** сессия (владеет `features/auth`) и текущий
  URL (владеет библиотека роутинга). Адаптер сессию не хранит, а читает и переводит.
- **Производное статичное** (считается один раз): пункты меню, структура маршрутов с лейаутом.
- **Производное динамичное** (пересчитывается, в state не хранится): результат guards,
  активный пункт меню.

### Перенесено на следующие шаги

- **I:**
  - отдельные фабрики или одна `createRouter(routes)`;
  - вывод типа параметров из пути через template literal types (`:id` → обязательный `{ id }`);
  - union имён страниц для `pages.config` (mapped + условный тип по `C[K] extends TPageRoute`);
  - проверка, что `redirectTo` и цели guards — имена из того же конфига;
  - сигнатура `Guard` и `checkAccess`.
- **O:** обёртка `AppLink` в `shared/ui` — если понадобится prefetch страниц или единое поведение
  ссылок. До тех пор — `Link` / `RouterLink` библиотеки + `buildPath`.
