# admin-templates

Учебный проект: шаблон админ-панели на React и Vue. Цель — отработать архитектуру компонентов
(что вынести в чистые функции, что в хук / composable, что оставить в компоненте) и архитектуру
приложения целиком. Итог — стартовая точка для любого проекта и материал для интервью, где можно
объяснить каждое решение.

## Структура репозитория

```
admin-templates/
  docs/               — регламент, договорённости, ADR
  react/              — React-проект, свой package.json  → react/README.md
  vue/                — Vue-проект, свой package.json    → vue/README.md
  scripts/git-hooks/  — скрипты проверок для git-хуков
  lefthook.yml        — конфигурация git-хуков
```

Пошаговая настройка каждого проекта — в его README. Здесь — то, что относится ко всему репозиторию.

## После клона

```bash
git clone git@github.com:vmasterov/admin-templates.git
cd admin-templates
brew install lefthook     # один раз на компьютер
lefthook install          # после КАЖДОГО клона — .git/hooks не хранится в git
cd react && npm install   # и/или cd vue && npm install
```

Удобно один раз настроить: `git config --global push.autoSetupRemote true` — первый `git push`
новой ветки сам создаёт её на GitHub (без `git push -u origin <ветка>`).

**Порты:** dev-сервер React — `3000`, Vue — `3000` (запускать по одному; если занят, Vite возьмёт
следующий свободный и напишет его в консоли), API по умолчанию — `http://localhost:3001`.

## Решения

Каждое решение: что выбрали → почему → чем заплатили.

### Один репозиторий, три независимые папки

- **Решение:** `react/`, `vue/` и `docs/` в одном репозитории — без npm workspaces и общих пакетов.
  Каждый проект ставится и запускается сам по себе.
- **Почему:** цель — два самостоятельных проекта, как в реальной работе, где обычно используется
  один фреймворк. Монорепо с workspaces связало бы проекты общими пакетами, а три отдельных
  репозитория неудобны для общего регламента в `docs/`. Плюс одна ссылка для портфолио.
- **Цена:** общий код не подключается пакетом — ядро `src/shared/lib` переносится между проектами
  копированием. Это же служит проверкой архитектуры: если ядро копируется без единой правки, логика
  действительно не зависит от фреймворка.

### Git-хуки через lefthook

- **Решение:** lefthook, установленный через brew; конфиг `lefthook.yml` в корне.
- **Почему:** git-хуки всегда живут в корне репозитория. husky и lint-staged потребовали бы
  `package.json` и `node_modules` в корне и связали бы проекты. lefthook запускает проверки только
  для изменённого проекта (`root` + `glob`) и только по изменённым файлам (`{staged_files}`).
  Любой проект выносится в отдельный репозиторий переносом его блока из конфига.
- **Цена:** хуки не ставятся автоматически при `npm install` (как `prepare` у husky) —
  `lefthook install` нужно выполнять после каждого клона.

### Хуки вызывают скрипты проектов

- **Решение:** хук запускает `npm run format | lint | test:related | build` внутри папки проекта,
  а не утилиты напрямую.
- **Почему:** каждый проект сам владеет своими командами. Хуку неважно, как проект линтит и
  тестирует, — он зависит от контракта (набора скриптов), а не от реализации (D из SOLID). Поэтому
  блок проверок описан один раз (YAML-якорь `&checks`) и используется для обоих проектов.
- **Цена:** каждый новый проект обязан предоставить эти четыре скрипта.

### Что проверяется при коммите

```
pre-commit (по очереди):
  1. branch-name — запрет коммита в main/develop, формат имени ветки
  2. для каждого изменённого проекта (React и Vue — параллельно):
       format → lint → test:related → build
commit-msg:
  3. Conventional Commits (проверяется первая строка сообщения)
```

- **Сборка на pre-commit, а не на pre-push:** коммит и пуш обычно делаются сразу друг за другом.
- **Без `--fix` в хуке:** хук — честная проверка, ошибку видно и правило запоминается.
  Автоисправление — в редакторе при сохранении.
- **`max-lines: 180` — рекомендация, а не правило ESLint:** автоматическая проверка подталкивает
  делить файлы искусственно.
- **`dist` после сборки не удаляем:** он и так в `.gitignore`.

Подробный разбор `lefthook.yml` и скриптов — `react/README.md`, шаг 5.

### Правила работы с git

- Коммит напрямую в `main` / `develop` запрещён. Работа — в ветках `<type>/<description>`
  (`feature/`, `bugfix/`, `hotfix/`, `refactor/`, `release/`, `chore/`, `docs/`, `test/`, `perf/`,
  `ci/`), в `main` — через pull request.
- Сообщения коммитов — по Conventional Commits: `<type>[scope]: <description>`.
- Если коммит упал на хуке — исправить ошибку и сделать обычный `git commit` заново.
  `git commit --amend` здесь не подходит: он заменит **предыдущий** коммит, а не создаст новый.
