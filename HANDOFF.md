# HANDOFF — admin-templates

Контекст учебного проекта для передачи между диалогами. Обновлён: 13.10.2026.

## Цель

Отточить навыки проектирования:
- **компонентов** — что вынести в чистые функции, что в хук (React) / composable (Vue), что оставить
  в компоненте;
- **приложения целиком** — структура, слои, связи между частями.

Итог: шаблон админ-панели в git (React и Vue) — стартовая точка для любого проекта, плюс проект для
интервью, где можно объяснить каждое архитектурное решение.

Ритм: занятия примерно через день, поэтому план считается в **сессиях**, а не в неделях.

## ⚠ Следующий шаг — сначала ТЗ

Прежде чем делать роутинг, нужно **придумать ТЗ проекта**: какая это админка, какие сущности, страницы,
роли, сценарии. Без него непонятно, какой будет роутинг и что вообще делать в Этапе 1. ТЗ прорабатываем
в новом чате. После ТЗ — Этап 1, тема «Роутинг», начиная с шага R по RADIO.

Черновик требований к роутингу (вход для ТЗ, ещё не согласован):
- публичные страницы: логин, 404;
- защищённые: дашборд, список и карточка сущности (`/users`, `/users/:id`);
- доступ по ролям (например, admin / viewer);
- редирект неавторизованного на логин с возвратом на исходную страницу после входа.

## Исходный план пользователя (первое сообщение)

```
Планы по написанию отдельных компонентов (на React и Vue)
Итог: шаблон админ-панели в git — стартовая точка для любого проекта

Этап 1 — Детали проекта: установка, роутинг, HTTP-клиент, авторизация, лейаут (хедер, футер, сайдбар)
Этап 2 — Компоненты:
  Tier 1: DataTable (сортировка, пагинация, фильтры), Form (валидация, состояния, submit),
          Modal/Dialog, Select/Dropdown (поиск, мульти-выбор), Toast/Notification
  Tier 2: Infinite Scroll / Virtual List, Tabs, DatePicker
Этап 3 — Архитектура минимум: SOLID на практике (пример на TS, как выглядит нарушение),
         RADIO Framework (спроектировать будущий проект, как на интервью — вслух)
Этап 4 — Продакшн проект: структура + базовый функционал, основные фичи,
         полировка/тесты/edge cases, деплой + документация
Итог: проект, который можно показать на интервью и объяснить каждое архитектурное решение
```

## Согласованный план (переработанный)

**Ключевые изменения относительно исходного:**
- SOLID и RADIO не отдельным этапом, а **применяются к каждой теме** с самого начала.
- Логика выносится в **чистый TS-слой** (`src/shared/lib`), хук/composable — тонкий адаптер.
- Вместо «повторять 5 дней» — итерации с усложнением (новое требование в последней сессии).

**Цикл одной темы (5 сессий):**
1. Дизайн по RADIO-мини: требования, API (props/events/slots), состояние, раскладка
   «core / хук / компонент».
2. Core + тесты (в React-проекте).
3. React-адаптер и компонент.
4. Перенос core во Vue **без правок** + Vue-адаптер и компонент.
5. Новое требование: с нуля по памяти, фреймворки чередуем; разбор, что сломалось и какой принцип
   SOLID нарушен.

Каждое решение записывается в `docs/` (короткий ADR: решение → почему → цена).

**Этапы:**
- **Этап 0 — Установка (~3 сессии)** — ✅ завершён.
- **Этап 1 — Каркас (~14 сессий):** роутинг → HTTP-клиент → авторизация → лейаут. Сокращённый цикл:
  дизайн + core → React → Vue. В core роутинга: описание маршрутов с метаданными (title, auth, роли,
  лейаут), guards как чистые предикаты, сборка URL с параметрами, позже меню и хлебные крошки.
- **Этап 2 — Компоненты (8 × 5 = 40 сессий):** Modal → Toast → Form → Select → DataTable → Tabs →
  Virtual List → DatePicker. a11y (клавиатура, ARIA) — в требованиях каждого компонента.
  Новые требования для сессии 5: Modal — стек модалок, фокус-трап; Toast — очередь с лимитом, ошибки
  HTTP → тост; Form — async-валидация, динамические поля; Select — асинхронные опции; DataTable —
  переход с клиентской пагинации на серверную; Tabs — синхронизация с URL; Virtual List — строки
  динамической высоты; DatePicker — диапазон, локаль.
- **Этап 3 — Продакшн-проект (~12 сессий):** RADIO всего приложения вслух (Claude — интервьюер) →
  фичи (например, мини-CRM) → E2E (Playwright) и edge cases → деплой, README, сводка решений.

Итого ~70 сессий, ~5 месяцев. **Открытый вопрос:** финальный проект на обоих фреймворках или на одном —
пересмотреть перед Этапом 3 по затраченному времени.

**RADIO** — фреймворк фронтенд-системного дизайна (GreatFrontEnd). Порядок шагов важен: каждый
следующий опирается на результат предыдущего. Применяется и к компоненту, и ко всему приложению.

| Шаг | Что это | Какие вопросы задаём | Результат |
|---|---|---|---|
| **R — Requirements** | Требования и рамки задачи | Какие сценарии? Что входит, что вне рамок? Нефункциональные: устройства, объём данных, a11y, i18n? | Список требований + «вне рамок» |
| **A — Architecture** | Из каких частей состоит решение и кто за что отвечает | Какие модули/слои? Как связаны? Компонент: что в core, что в хуке/composable, что в компоненте. Приложение: роутинг, API-клиент, состояние, UI | Схема частей и связей |
| **D — Data model** | Какие данные есть и где живут | Серверные данные или клиентское состояние? Что хранить, а что вычислять (пример: `getArticleStatus`)? Форма состояния, нормализация | Типы и структура состояния |
| **I — Interface** | Контракты между частями | Компонент: props / events / slots. Core: сигнатуры функций. Сервер: эндпоинты, запрос/ответ | Сигнатуры и контракты |
| **O — Optimizations** | Качество сверх «работает» | Производительность (виртуализация, мемоизация, debounce, кэш), a11y (клавиатура, ARIA, фокус), UX (загрузка / ошибка / пусто), edge cases, безопасность | Список улучшений с приоритетами |

Ориентир по времени на интервью (GreatFrontEnd): R ~15%, A ~20%, D ~10%, I ~15%, O ~40% — основная
оценка идёт на шаге O, поэтому первые шаги проходят быстро и по делу.

**Договорённость:** пользователь раньше RADIO не знал — на каждой сессии дизайна явно помечать шаг
(R/A/D/I/O), объяснять, зачем он и какие вопросы задаются, в конце показывать, как результат шага
повлиял на код.

## Принятые решения и причины

- **Один репо, три независимые папки** (без workspaces): два самостоятельных проекта + общий `docs/`.
  `shared/lib` переносится копированием — это и проверка, что ядро не зависит от фреймворка.
- **Структура `src/`:** `app/ pages/ features/ shared/{lib,ui,api,config}`; импорты только сверху вниз
  `app → pages → features → shared`. FSD отвергнут как избыточный.
- **lefthook** (brew) вместо husky + lint-staged: корень без npm; проверки только изменённого проекта
  и файлов. Цена: `lefthook install` после каждого клона.
- **Хуки вызывают скрипты проектов** (контракт `format`, `lint`, `test:related`, `build`), блок
  проверок один на оба проекта через YAML-якорь `&checks`.
- `pre-commit` (`piped`): `branch-name` → проекты параллельно, внутри по очереди
  `format (stage_fixed) → lint → test:related → build`. `commit-msg`: Conventional Commits, проверка
  только первой строки (`head -n1`; иначе проходили merge-коммиты).
- Скрипты `lint: "eslint"`, `format: "prettier --write"` — **без `.`**, чтобы хук передавал файлы.
- **Сборка на pre-commit** (коммит и пуш идут вместе); `dist` не удаляем.
- **Без `--fix` в хуке**, автоисправление — в WebStorm при сохранении.
- **`max-lines: 180` — рекомендация, не правило ESLint** (не делить файлы искусственно).
- TS: `strict` явно; `paths` без `baseUrl` (устарел в TS 6).
- Docker: `node:22-alpine` (Node 20 EOL), без `max_old_space_size`.
- Порты: React 3000, Vue 3000 (пользователь оставил), API 3001.
- Git: ветки `<type>/<desc>`, в `main` только через PR; `push.autoSetupRemote` включён;
  после упавшего хука — обычный `git commit`, не `--amend`.
- Скрипты хуков — в отдельных файлах (цвета оставлены), не inline в YAML.

## Открытые вопросы / на потом

- **ТЗ проекта** — следующий шаг (новый чат).
- Финальный проект: оба фреймворка или один — решить перед Этапом 3.
- Vue: `noUncheckedIndexedAccess` есть только во Vue — добавить в React или убрать (единообразие);
  дублирующиеся опции в `vue/tsconfig.app.json`; удалить `@vitejs/plugin-vue-jsx`, если JSX не нужен;
  алиас Vue можно перевести на `tsconfigPaths: true`; порт Vue (сейчас совпадает с React).
- Для тестов компонентов: Vue — `jsdom` + `@vue/test-utils`, React — `jsdom` +
  `@testing-library/react` (поставить при первом компоненте).
- `commit-msg`: при появлении локальных merge/revert добавить пропуск
  `^(Merge |Revert "|fixup! |squash! |amend! )`.
- WebStorm показывает предупреждение о типах на `prettierConfig` в `vue/eslint.config.js` —
  безвредно, ждать обновления `@vue/eslint-config-typescript`.
- `docs/` пока пуст — начать вести ADR с роутинга.
